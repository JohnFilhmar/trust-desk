# AI usage

What the AI generated in each phase, and what I changed or rejected. I fill in the second part when I review each pull request.

I kept my own prompts in `docs/prompt-log.md`.

## How the AI was used

- **Agent:** Claude Code, running on its own toward a stated goal, with two conditions under which it had to stop and wait for me.
- **Context I maintained:** `CLAUDE.md` for this repository, my global `CLAUDE.md`, and my own skills for project structure, TypeScript style, testing, documentation and writing.
- **Decisions:** real trade-offs went to a council of three advisors and a chair. Each verdict is recorded in an ADR, marked provisional until I confirm it.
- **Review:** one pull request per phase. I merge, nobody else.

## Phase 1: walking skeleton

### How the work was split

The main agent wrote the parts everything else depends on: the seven migrations, the grants policy, the shared zod schemas, the JSON fixtures and the signing test vectors. With that contract fixed, three parts were built at the same time:

| Part | Built by | Checked by |
|---|---|---|
| Handlers | the main agent | its own tests |
| Rails | a subagent, from a written brief | the main agent ran every test, RuboCop and Brakeman again, and read the security-critical files |
| Web console | a subagent, from a written brief | the main agent ran every test, the typecheck and the build again, and scanned for banned patterns |

Each subagent was confined to one directory, could run no git command and could add no dependency. Neither report was taken on trust.

### Generated by the AI

- Seven migrations, the two triggers, and the column-level grants.
- The shared contract: schemas for every request and response, four JSON fixtures, and the script that writes the signing vectors.
- Eight handlers, the router with its fixed order of checks, the session cookie, the masking module, the signed client and the queries.
- The Rails side: eight models, the signature check, the suspend endpoint, the service object, three serializers and the seed.
- The web console: the API client, the providers, four pages, the suspend dialog.
- Two Playwright tests.
- The Rails learning guide sections for the request lifecycle, fifteen concepts, the magic list and the reading path.

### Decisions the AI took without me

| Decision | Why | Where |
|---|---|---|
| PII is masked for every group in this phase | Reveal arrives in Phase 2, and a skeleton should not leak by omission | design note |
| Code checks a permission, never a group name | One map from group to permissions, tested against one fixture on both sides | `packages/shared/fixtures/group_permissions.json` |
| A stateless signed session cookie, 8 hours | No session table to build or clean up. The cost is stated in the design note | `session_cookie.ts` |
| A row lock, not optimistic locking | The second enforcer gets a 409 about the account, not a retry error about a version | `suspend_account.rb` |
| A route has no default access level | A route that names no access does not compile | `types/handler.ts` |
| `APP_ORIGIN` became `APP_ORIGINS`, a list | The end-to-end container has an origin of its own | `config/env.ts` |
| The placeholder bcrypt hash is generated at startup | The first version was a made-up string the agent could not prove valid | `lib/auth/password.ts` |
| The web app injects its API client | `jest.mock` is not hoisted in this setup | `ApiClientProvider.tsx` |
| The seed became the reset as well | One command, one code path, the same data every time | `db/seeds.rb` |

### Mistakes the AI made and caught

- It wrote a made-up bcrypt string and called it a valid hash. An invalid hash would be refused at once, which reopens the timing gap the placeholder exists to close. Replaced before it was ever committed.
- It began changing a shared schema while both subagents were building against it. It noticed, restored the file, and held every contract change until both had reported.
- The learning guide said a Rack middleware parses the JSON body, and that the SQL log appears in the container's output. Both were wrong. Running `bin/rails middleware` and reading the log file corrected them before the guide was committed.

## Phase 2: complete core

### How the work was split

The same split as Phase 1, with the same limits on each subagent. The main agent extended the shared contract and wrote the handlers first, then briefed each subagent in writing against that contract.

One thing changed in how the main agent worked. In Phase 1 it started to change a shared schema while both subagents were building against it. In Phase 2 it added new schema files freely, since nothing depended on them yet, and held every change to an existing schema until the subagent that used it had reported.

### Generated by the AI

- The contract for risk, events, reveal and operational modes, and two more fixtures.
- Seven handlers, the risk score and its config, the read path with its fallback, payload masking, the login throttle, the client IP resolver.
- The Rails side: unsuspend, mark as spam, the reveal audit, mode changes, idempotency, the advisory lock, the correlation id on every log line, and a seed that now leaves accounts suspended and marked.
- The console: the risk column and panel, the search form, reveal, the timeline, the mode banner and dialog.
- Seven more Playwright tests, which follow the demo script.
- The production Compose file, the host nginx config, the deploy runbook, and a script that checks the production images.
- The README, the demo script, the interview notes and the exercises.

### Decisions the AI took without me

| Decision | Why | Where |
|---|---|---|
| A reveal needs a reason | An audit row that says who and what is half an answer | design note, decision 1 |
| A viewer searching by PII gets 403, not an empty list | A refusal should not look like "no match" | `search_accounts.ts` |
| The list shows a quick score, the account page the full one | A page of 25 would need about 150 queries to score in full | design note, decision 4 |
| The idempotency key travels in the signed body | So the signature covers it | design note, decision 5 |
| Only a success is stored under an idempotency key | An analyst can fix a refusal and send again | `idempotent_request.rb` |
| Revealed values never enter the query cache | A cached value outlives the page. The dialog holds its state in plain React state for that reason | `ReasonDialog.tsx` |
| A parent class with three children for enforcement | Each child reads like a row of the rules table, and the shape is one a TypeScript developer knows | `account_enforcement.rb` |
| An advisory lock for mode changes | The mode has no row to lock, since every change is a new row | `change_operational_mode.rb` |
| Prepared statements stay off | Switching them on crashed Ruby | `CLAUDE.md`, gotchas |
| Browser tests run one at a time | One of them puts the console in lockdown | `playwright.config.ts` |
| The production images were run locally first | Two bugs exist only in the hardened image | `docs/bug-log.md`, 003 |
| No solutions branch for the exercises | The brief says both "do not solve them for me" and "put the solutions on a separate branch". The AI raised it and wrote none | `docs/rails-exercises.md` |

### Bugs found

| Bug | Found by | Whose fault |
|---|---|---|
| 002, the console failed on plain HTTP | the first Playwright run | the brief the main agent wrote named a function that does not exist there |
| 003, production Rails never started | running the production images locally | the main agent's Compose file |
| A focus bug left from Phase 1 | the web subagent, while refactoring | a Phase 1 test had passed only because a refresh answered at once |

### Mistakes the AI made and caught

- Two of its own Playwright assertions were wrong. One matched "Unsuspend account" when it meant "Suspend account". One found an event type in the filter's dropdown and took it for an event. The app was right both times. The tests were fixed, and the app was not touched.
- It started two builds of the same image at once, and one failed. The images were fine.
- It documented an integration test command it had not run in that exact form, then replaced it with the one it had.
- A code snippet in the learning guide used a shorthand the real file does not use. Replaced with the real code.

## What the AI could not do

- **Run CI.** GitHub refused every job: "recent account payments have failed or your spending limit needs to be increased". Every check the workflow would run was run locally in Docker. The workflow file itself has never run.
- **Create `.env.example`.** My settings deny writes to that path. The list is in `docs/env-reference.md`.
- **Deploy.** It has no access to the server. The runbook is written and the production images are tested locally.
- **Set its own goal, or push to `main`.** Both are mine to do.
