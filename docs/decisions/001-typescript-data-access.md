# 001: TypeScript data access

Status: provisional. Decided by the council on 2026-09-30 while I was away. I confirm or overturn it on the Phase 0 pull request.

## Context

The handlers read MySQL 8. Rails owns the schema and the handlers never migrate. There are 10 to 15 queries: JSON path lookups, indexed generated columns, keyset pagination on `(created_at, id)`, a fallback aggregation over raw events, and lookups that span accounts.

The job description lists "SQL (MySQL, including JSON column querying)" as a must-have. The house rules ban `any` and `as` casts, and ask for zod at every boundary.

## Options

- **A.** Raw SQL through `mysql2` with prepared statements, every row parsed by a zod schema.
- **B.** Kysely, a typed query builder. Its database types are hand-written or generated by a codegen tool, which would be one more dependency.

## The council's verdict

Three advisors and a chair. No peer-review round.

**Agreed, all three:** option A.

- Kysely's types would be a hand-written copy of a schema Rails owns. When Rails migrates, the copy keeps compiling and is wrong.
- Kysely checks nothing at runtime, so zod is still needed on every row. That is two type systems for one guarantee.
- JSON path lookups and the row-value keyset comparison would land in Kysely's raw `sql` tag anyway.
- The posting scores SQL, so SQL an interviewer can read is the exhibit.

**Disagreed:**

- *What handlers receive.* One advisor wanted a generic `query` helper on `deps`. Two wanted named functions and never the pool. The chair kept both at different layers: the helper is internal, and `deps.db` exposes named functions only. A generic helper on `deps` would force tests to mock by SQL string.
- *`dateStrings` or `timezone`.* They fix different problems. A JavaScript Date holds milliseconds, so a `datetime(6)` cursor read into one skips or repeats rows. `dateStrings: true` fixes that. `timezone: 'Z'` covers any Date that is bound as a parameter. The pool sets both.

**Caught by one advisor only:** tests with a mocked database prove nothing about the SQL. Each query also gets a test against real MySQL.

## Decision

Option A.

- `src/lib/db/run_query.ts` is the internal helper. It treats the driver's result as `unknown` and parses it with zod.
- One file per query, holding the SQL, the row schema and the exported function.
- `deps.db` exposes named functions. Handlers never see SQL or the pool.
- The pool sets `dateStrings: true` and `timezone: 'Z'`.
- A `LIMIT` is validated as an integer and bound as a string, since MySQL 8 rejects a numeric one in a prepared statement.

## Consequences

- No query builder to learn or explain, and no new dependency.
- Nothing checks a query against the schema at compile time. A renamed column is caught by the integration test for that query, not by the compiler.
- Row schemas must match what the driver returns, not what the table declares: JSON columns arrive parsed, and `DECIMAL` and `SUM()` arrive as strings.
